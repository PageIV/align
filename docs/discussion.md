# 讨论结论

我认为值得回看的结论，从讨论里精简后存这里。按时间倒序，新条目加在最上面。

**和另外两份文件的分工**：

- `ALIGNMENT.md` 是插件管的已确认项，每轮自动注入，**不要手改**——那是给 Agent 看的。
- `docs/adr/` 是正式的架构决策记录，一个决定一份，带状态。
- 这份是给我自己回看的：**讨论出了什么、为什么、代价是什么**。够长期、够正式的结论应该升级成 ADR；这份留着不删。

每条的写法：结论 → 理由 → 代价与边界 → 搁置的备选。写的时候假定读者是三个月后的我，不记得上下文。

## 2026-10-05 · 指令性断言每轮注入的风险，与"三个目的地"的解法

**起因.** C-007（"面板那条落地路径退役，落地统一走 `align_land`"）这类**命令式**断言落进了账本。账本每轮全量注入——这种句子会不会影响模型？

**会，而且影响是无条件的。** 四层：

1. **位置决定身份.** 注入贴在用户当前消息**后面**到达，位置上就是用户消息的一部分。写成命令的断言读起来等于"用户此刻又吩咐了一遍"，每轮吩咐一遍是最强的指令。
2. **优先级规则原本缺一半.** 原来只写"与上文对话冲突时以此为准"——那只管"陈旧对话 vs 账本"。第三种情形没管：**用户当前这句话 vs 账本**。而注入在位置上晚于用户的话，真撞上时后出现的反而可能占上风。已修：HEADER 改成三级——与更早的对话冲突时以账本为准，**但用户当前这条消息的要求优先**。
3. **命令式措辞会放大.** "退役""统一走"是派活，不是前提。更好的写法是描述："落地只有 `align_land` 一条路。"每轮重复几十次之后，这个差别会被放大。
4. **累积效应是真风险.** 攒十几条命令式条目之后，模型每轮都要在"眼前这件事"和"一叠长期命令"之间分配注意力，久了会变成规则执行器。这是"策展是面板第一职责"的第二个理由——不光省 token，更是别让旧决定盖过眼前的事。

**另一个角度（更远）：** `ALIGNMENT.md` 是项目文件、能进 PR。别人 clone 一个带账本的仓库，钩子就会把里面的内容每轮注入到你的上下文，而且是用户级位置——等于给仓库作者开了一条常驻指令通道。现在没有防护（钩子只认 `cwd` 下有没有账本）。等真出现多人协作再处理，但不该忘。

**解法：给命令式/一次性的东西换个目的地。** 表单不再让用户选分类标签，只让人选**去哪**：

| 选项 | 去哪 | 活多久 |
| --- | --- | --- |
| 不写入 | 不落盘 | — |
| 写入 | `ALIGNMENT.md` → 热块 | 每轮注入，直到退休 |
| 复述 | 收件箱（如 `.align/inbox.md`） | 下一次提问注入一次，随即销毁 |

- **分类退回成标签.** 用户不选类型之后，类型唯一的行为效果（`restate` 策略）就没有了——`[types.*] restate` 可以从配置里删掉，类型只剩"给人看的标签"。热块行首的前缀保留（便宜），标错只影响展示，不影响行为。
- **默认停在模型建议上.** 表单默认值 = 调用 `align_land` 的那个 Agent 给的建议。它本来就要把侧聊结论压成候选断言，现在每条多填一个"建议去哪"的字段——**零额外模型调用**。（对比：旧的复述卡片走 `ui/message`，会额外触发模型跑一轮；收件箱搭在下一次提问上，不额外触发。）
- **"命令式的用完就失效"由用户那一勾实现**，不是靠模型背后猜。两种错法都会静默：长期前提被判成一次性会悄悄消失（这正是产品要治的病），一次性指令被判成长期则每轮重复。显式反而更便宜——表单本来就是每条一次选择，换成三个目的地是更少负担、更强控制；默认值停在模型建议上，则既不费神也不失灵。

**一个被否掉的实现：输入框上方那个小框.** 用户提议像 Codex 的"添加到对话中"那样，把带回的内容显示成输入框上方的小框。那个机制是 `ui/update-model-context`，探针里验过，形态完全对得上。但它有两个绑死：必须有活着的 MCP App 面板去调它（面板关掉报 `-32000`）；而且只作用在**面板所在的那个会话**——侧聊里开的小框出现在侧聊输入框上，不会跑到主线程。它做不了"侧聊 → 主线程"。跨会话只有文件加钩子，而钩子的投递是隐形的。要让带回来的东西被看见，可以在注入内容里附一句"请把它显式复述给用户"——它会以一条可见消息落在主线程里，一次，且不额外调用模型。

**验证结果（2026-10-05，探针实测）.** 收件箱的定向问题问清楚了：

- **侧聊会触发钩子**（`UserPromptSubmit` 在侧聊里照常跑，日志有行）。
- **侧聊的 `session_id` 与主线程不同**：主线程 `01a10a1a-714c-…`，侧聊 `01a10b68-b97e-…`。所以两者**可区分**。
- 宿主是拿 `thread/fork` 造出侧聊的，日志里能看到；但**钩子输入里没有"从哪条主线 fork"这个字段**，只有它自己的 `session_id`、`turn_id`、`cwd`、`transcript_path` 等。

**由此定的投递规则.** 收件箱条目记下"是谁写的"（写入时的 `session_id`），**在下一条不属于该会话的提问上投递，投递即消费**。侧聊里落的"复述"因此不会被侧聊自己的下一句话吃掉，会等到你回主线程时送达。反过来，在主线程里落的"复述"不走收件箱——工具结果直接让当前这轮把它说出来即可，本来就在同一个会话里。

**补丁（同日晚些时候，第二个探针）.** 上面那条规则漏了一种情况：**新开一个侧聊**。新侧聊的 `session_id` 与写入者不同，会直接把条目认领走，主线程永远等不到。宿主这边查不到"这条会话是不是侧聊"——侧聊根本不落库（`threads` 表、`thread_spawn_edges`、`~/.codex/sessions/` 都没有它）。

但钩子输入里有一个现成的判据：

```
主线程  transcript=/Users/page/.codex/sessions/…/rollout-…-01a10a1a-….jsonl
侧聊    transcript=null
```

侧聊没有 rollout 文件，`transcript_path` 就是 `null`。（`agent_type` / `agent_id` 两边都没有，指望不上。）

所以最终规则是：**只在 `transcript_path` 非空、且不是写入者的会话里投递并消费。** 判"这是不是侧聊"的能力顺带也留下来了，将来别的功能要用可以直接捡。

附带两条待观察：条目若一直没人去"别处"提问，会一直躺着，需要过期策略（先不做）；全新线程的第一条消息可能 rollout 还没建立、`transcript_path` 也是 null，那条消息不会投递，第二条才送到。

## 2026-10-05 · 清理：丢掉线程层落地与 promote，复述保留但放宽

**结论.** 线程层落地（`ui/update-model-context` 一次性附着）作废；提升（promote）作废；**复述保留，语义放宽**；线程作用域暂缓。

**为什么.**

- 线程层落地是一次性的，之后靠对话历史承重、压缩即失效——而需求是"每轮都要拿到"，只有落文件能满足。每轮注入改走 `UserPromptSubmit` 钩子。
- 提升唯一的用途是把线程层条目救进项目层。线程层没了，它就没有对象。
- **复述保留，而且比原来更重要。** 它不只是"落地后的回执"，也是**把侧聊里一段带回主线程的通道**——那段内容可以够不上一条断言。侧聊里聊出了点东西、值得让主线知道、但不必进账本，走的就是它。
- 线程作用域暂缓：钩子拿得到 `session_id`，按线程渲染技术上可行，但还没定它要解决什么问题。多一层状态，就多一层和压缩、fork、侧聊分叉纠缠的麻烦。

**边界.** 有一条纪律跟着改了：侧聊**能**调工具，也能改工作区——宿主只在用户明确要求时才放行。所以"侧聊只用来追问、落地一律回主线程"不再成立。

**留一行理由.** 这些废弃项在 `spec.md` 末尾有一节"已废弃的设计（为什么放弃）"。动机本身（"只在这轮成立的修正不该污染仓库"）是站得住的，不写清楚，将来还会被重新提出。

## 2026-10-05 · 钩子每轮注入：全量重播，不做增量

**结论.** 钩子每轮注入当前生效的**全部**已确认项。不做"只注入新增/变更"的增量方案。成本靠两道闸压住：热块硬上限，加上把"删和退休"做成面板的第一职责。

**为什么不做增量.** 这个产品的立论是"旧上下文会失去力量"——上下文一长，Agent 就跑偏。热块每轮重播的全部功能，就是对抗"这条前提已经离我很远了"。只在有变动时注入，等于每条断言在注入后的第二轮就开始变旧；省下的 token 是从它唯一的价值里省的。注入越省，越退回产品要治的那个病。

另外三个工程坑：

1. 需要每线程的"已送达"状态（`session_id` 有，但要落盘），接着就要处理线程删除、fork、侧聊分叉、进程崩溃。
2. 压缩会打断它的前提——"注入过"不等于"还在上下文里"，压缩后必须全量重播，于是多出两条路径和一个切换判断。
3. 失败是**静默漏报**：模型少看到一条前提，按错的前提继续干，没有任何信号。这正是这个产品存在的理由。

**风险不对称.** 漏报的代价隐性且昂贵，重复的代价显性且可调。不对称就该往多注入那侧偏。

**关于"重复会不会让模型变差".** 没有证据说会。已知让模型变差的是噪声、互相矛盾、篇幅过长，以及同一条内容反复出现却已经过期（频率被读成重要性）。所以真正的风险不是重复，是**没有上限的增长**和**该退休却没退休的条目**——那是策展问题。

**两笔成本要分开算.**

- 每轮注入本身：6 条约 500 token，落在消息尾部，前面的提示缓存不受影响，可忽略。
- **历史里的堆积**：每轮追加一份，30 轮后历史里躺着 30 份，一万多 token，直到压缩才被吃掉。**这才是真成本**，也是压成本该瞄准的地方。

**当时定的配套手段.**

1. 热块限在十来条一行式条目，超出的留在账本里但退出热块。
2. 注入里带修订号（`items=` 已有，再加 `rev=`），让模型一眼看出"自上轮没变"，省的是读取成本，不是内容的存在。
3. 条目按最近变更排序。
4. 账本涨到几十条再上分层：常驻层每轮全文 + 其余压成一行索引（"另有 N 条，涉及 X / Y / Z 时用 `align_list` 读全文"）。

**搁置的备选.** 增量注入。不是永远否掉——如果哪天实测出"重复注入"有可观测的负面影响，再翻案。在此之前不做。
